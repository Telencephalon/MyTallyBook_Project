## 4. 本次问题与处理方法

| 现象 | 原因 / 判断 | 实际处理及以后注意事项 |
|---|---|---|
| `java: command not found` | shell 没有通用 java 命令，不代表其他业务没有自带 Java | 安装 Java 21，本项目 unit 固定绝对路径；不动 Resin 的 Java 8 |
| 查 `mysql` inactive | 查询了默认服务名 | 使用 `mysql8.service` 和 `/opt/mysql8/bin/*`；不要另装一套 MySQL |
| Certbot `Incorrect TXT record` | CA 查询到旧挑战值；DNS 面板改完不等于公共解析已更新 | 保存记录后查询权威/公共 DNS，确认等于**当前这次** Certbot 值再回车 |
| 每次重试 TXT 都变化 | 新申请可能生成新挑战 | 保留当前等待窗口，复制完整当前值；不要循环重启申请后继续用旧值 |
| 清 DNS 缓存仍返回旧 TXT | 本机清缓存不能清公共递归 DNS 缓存 | 等待 TTL 与权威传播；本次 TTL 为 10 分钟，不能保证恰好 10 分钟完成 |
| curl `Could not resolve host` | 当时的本地 DNS 解析未就绪 | 分别查询 A 记录，必要时清本机缓存；最终用不绕过 DNS 的正常 HTTPS 请求验收 |
| Nginx 安装提示 80 已占用/未自动启动 | 80 属于其他业务；安装器阻止默认站点启动 | 使用项目 HTTPS 安装器管理 443；以最终 nginx -t、服务状态和 HTTPS 为准 |
| Windows DPAPI 文件不能直接用于 Linux | 加密数据绑定本机/用户使用场景 | 不把 dpapi 文件当 env；本次用户手工填写服务器配置 |
| 密钥自动导出被 `blocked by policy` 拒绝 | 自动审批拒绝，未提供更具体原因；用户授权后重试仍被拒绝 | 没有继续绕过；没有生成部署密钥文件，改为用户受控填写 |
| 原 Token Pepper 无法取得 | 自建随机秘密，不是向微信“重新申请”的值 | 用户生成新值后旧登录会话、旧邀请失效；重新登录/重新邀请；原账目与成员不因轮换被删除 |
| `reset-failed ... Unit ... not loaded` | 首次启动顺序中多余命令失败，set -e 导致后续 start 未执行 | 首次用 daemon-reload、cat、start，再等待 UP；已加载且触发启动限流时才需要 reset-failed |
| `current.jar` 显示 root:root 777 | 显示的是软链接本身权限 | 用 `stat -L` 和 `runuser -u accountbook -- test -r` 检查目标文件，不改软链接权限 |
| 微信上传 `10_000` 非法语法 | 该次上传编译链未处理数字分隔符 | 源码改为 `10000`，超时仍是 10 秒；本地测试不能替代上传验证 |
| 微信上传 `Unexpected token .` | `?.`/`??` 保留到上传产物，原 es6/enhance 均关闭 | 同时开启两项、重新编译再上传；不要只修改临时生成的 env.js |
| 上传提示类型文件“无依赖文件” | 纯类型在编译后没有运行时引用 | 本次四个 types 文件已核对为类型声明，正常；不能据此认定所有被忽略文件都无用 |
| API 未登录返回 401 | 身份认证正常拒绝匿名请求 | 预期是项目 JSON `AUTHENTICATION_REQUIRED`；它只证明入口正常，不代表业务测试完成 |

### 5.3 手工 DNS-01 证书

服务器 Bash，仅首次申请或到期前手工续期时执行：

```bash
apt-get install -y certbot
certbot certonly --manual --preferred-challenges dns \
  --cert-name www.cr-chenny.com -d www.cr-chenny.com
```

在 DNS 平台填写：

| 字段 | 值 |
|---|---|
| 主机记录 | `_acme-challenge.www`，平台会追加 `.cr-chenny.com` |
| 类型 | TXT |
| 记录值 | 当前 Certbot 窗口给出的完整值，保留大小写、连字符、下划线 |
| TTL | 本次为 10 分钟 |

点击保存后，保持 Certbot 在 `Press Enter to Continue` 等待；另开 PowerShell：

```powershell
Resolve-DnsName cr-chenny.com -Type NS
Resolve-DnsName _acme-challenge.www.cr-chenny.com -Type TXT -Server 223.5.5.5
Resolve-DnsName _acme-challenge.www.cr-chenny.com -Type TXT -Server 119.29.29.29
```

必要时把 `-Server` 换成上一步返回的权威 DNS。各次查询可能因缓存不同返回不同结果；确认新值传播后再继续验证。不要把截图中的历史挑战值复制到新的申请。

签发后检查：

```bash
openssl x509 -in /etc/letsencrypt/live/www.cr-chenny.com/fullchain.pem \
  -noout -dates -ext subjectAltName
```

DNS-01 使用 TXT 验证域名，不需要占用 80；本项目不使用需要 80 的 HTTP-01。依据：[Let's Encrypt 验证方式](https://letsencrypt.org/docs/challenge-types/#dns-01-challenge)。续期见第 13.3 节。

草稿不能代替真实可用的审核路径。隐私表单应按代码实际收集/处理的数据填写；运营方展示名与平台登记主体的关系以真实资料为准，不为通过审核填入不实内容。本次没有登录后台代填或提交。

### 9.5 审核结果与正式发布

- **审核中：** 保持审核版本对应 API 可用，避免破坏接口、邀请或测试数据；体验测试并不意味着可以停后端。
- **审核驳回：** 记录原因，判断是资料问题还是代码问题。资料问题按后台补正；代码问题修复、重新测试、上传新版本，再按后台流程提审。
- **审核通过：** 在后台确认版本和发布方式后执行“发布”。审核通过本身不等于已经正式发布。
- **发布后：** 用正式入口重新微信登录、读取原账本并完成受控记账验证；检查服务器日志、备案展示和实际接口地址。体验版会话可能与正式版分别存储，需要重新登录是可预期情况。
- **留档：** 记录上传版本、审核编号/结果、发布时间、后端 JAR、Flyway 版本及验收人。

页面名称可能随平台更新，以当前后台可见项为准；本次提供的是操作指南，不代表已完成审核或发布。

### 10.2 根据修改内容选择流程

| 改动 | 修改位置 | 验证 | 上线动作 |

| 运行参数/密钥 | 服务器 `account-book.env` | 参数合法性、健康与登录 | 受限备份 → 编辑 → restart → 验收；一般无需重打 JAR |

| 仅 README/手册 | 文档 | 命令与代码核对 | 无需发布应用 |

### 10.3 数据库变更原则

- 已上线的 V1～V4 文件不重写、不改 checksum。新功能使用新迁移；实际下一版本以当前仓库为准。
- 本地启动器当前还固定核验 V1～V4 清单与目标版本；新增迁移时需同步审查相关清单/测试/目标版本，不通过跳过验证启动旧包。
- 优先先新增兼容字段/表，后端同时兼容旧客户端；等新版普及、旧路径确认停用后，再安排删除旧字段。
- 启动新 JAR 可能已经执行迁移，即使后来启动失败，也不能假定数据库没有变化。MySQL DDL 不应被当成能整体自动撤销。
- 迁移有数据重写/不可逆删除时，必须先在隔离恢复库演练，制定停写窗口、数据核对与恢复方案。
- 不用 `ddl-auto=update`、Flyway clean/repair 或手工删字段作为日常升级捷径。

### 10.4 前后端发布顺序

常规同时改前后端时：

```text
兼容性设计
→ 独立环境开发与测试
→ 备份正式库
→ 部署仍支持旧小程序的后端
→ 验证旧小程序继续正常
→ 上传新小程序并验收体验版
→ 提交审核，审核期间保留旧接口
→ 正式发布新小程序
→ 复验并观察
→ 另一个版本再清理已停用能力
```

微信审核和客户端更新不会与服务器发布同时完成，旧客户端可能继续访问。当前体验版也使用正式后端，新后端上线时立即影响现有客户端，不能等到小程序发布当天才考虑兼容性。

## 11. 后续每次更新与上线操作

### 11.1 发版前

1. 确定版本号、范围、是否有迁移、旧客户端兼容性与回滚条件。
2. 在主目录检查改动；记录源码版本和尚未提交的变更范围。不要用 reset/clean 清除现有工作，也不把密钥提交到 Git。
3. 按第 7.1 / 9.2 节运行相关验证，数据库变化额外跑隔离库验证；测试失败停止发版。
4. 按第 7.2～7.3 节生成唯一发布包并上传。仅前端修改可以跳过后端打包部署。
5. 选择短维护窗口，告知实际受影响使用者。当前单后端更新需停服，期间可能返回 502，不能承诺零停机。
6. 记录旧 JAR、数据库备份、配置备份。只有修改了对应配置才进行配置发布。

**现有脚本限制：** 不直接使用 `deploy.ps1 -Apply` 作为生产一键部署入口。它没有传入当前正式库名，默认备份 `account_book`，且未为本机 MySQL 工具补 PATH。`install-release.sh` 默认重启后只立即检查一次健康状态，可能误回滚。因此使用以下可观察步骤；这些脚本优化属于后续工作。

### 11.2 服务器后端升级

先校验新包并记录旧版本；服务器 Bash：

```bash
(
set -euo pipefail
umask 077
RELEASE_ID='替换为本次发布编号'
[[ "$RELEASE_ID" =~ ^[0-9]{8}-[0-9]{6}$ ]] || exit 1
STAGE="/root/server-upload-$RELEASE_ID"
cd "$STAGE"
sha256sum -c SHA256SUMS
bash -n install-release.sh
test ! -e "/opt/account-book/releases/account-book-server-$RELEASE_ID.jar"

OLD_JAR=$(readlink -f /opt/account-book/current.jar)
case "$OLD_JAR" in
  /opt/account-book/releases/*.jar) ;;
  *) echo '旧 JAR 路径异常，停止'; exit 1 ;;
esac
test -f "$OLD_JAR"
RECORD="/root/account-book-release-record-$RELEASE_ID"
mkdir -m 0700 "$RECORD"
printf '%s\n' "$OLD_JAR" > "$RECORD/previous-jar-path.txt"
sha256sum "$OLD_JAR" > "$RECORD/previous-jar.sha256"
cp -p /etc/account-book/account-book.env "$RECORD/account-book.env"
cp -p /etc/systemd/system/account-book.service "$RECORD/account-book.service"
if [ -d /etc/systemd/system/account-book.service.d ]; then
  cp -a /etc/systemd/system/account-book.service.d "$RECORD/"
fi
echo "发布前记录目录：$RECORD"
)
```

此目录含环境密钥，只能作为服务器受限备份，不能截图、发聊天或提交仓库。以上成功后：

1. 执行 `systemctl stop account-book.service`，确认本项目停止；不要停 MySQL、Nginx 或 Resin。
2. 按第 5.5 节或第 13.1 节备份正式库；失败则停止升级。在尚未修改数据库/配置/链接时，可启动原服务恢复使用，再排查备份。
3. 记录实际备份路径、校验结果，确认迁移已演练且满足本次回滚条件。
4. 执行下面的安装块。各块是独立会话，重新填写相同发布编号。

```bash
(
set -euo pipefail
RELEASE_ID='替换为同一发布编号'
[[ "$RELEASE_ID" =~ ^[0-9]{8}-[0-9]{6}$ ]] || exit 1
STAGE="/root/server-upload-$RELEASE_ID"
cd "$STAGE"
sha256sum -c SHA256SUMS
test ! -e "/opt/account-book/releases/account-book-server-$RELEASE_ID.jar"
test -f "/root/account-book-release-record-$RELEASE_ID/previous-jar-path.txt"

if systemctl is-active --quiet account-book.service; then
  echo '后端尚未停止；先停写并完成备份'; exit 1
fi

# --no-restart 仍会清理旧包；本次保留现有全部版本，验收后再整理。
KEEP_COUNT=$(( $(find /opt/account-book/releases -maxdepth 1 -type f -name '*.jar' | wc -l) + 1 ))
bash ./install-release.sh \
  --artifact "./account-book-server-$RELEASE_ID.jar" \
  --sha256 ./SHA256SUMS --keep "$KEEP_COUNT" --no-restart
runuser -u accountbook -- test -r /opt/account-book/current.jar
readlink -f /opt/account-book/current.jar
)
```

完成后执行第 7.5 节启动等待，再做第 8 章公网检查及旧客户端业务验证。仅 JAR 更新时，**不重新安装 service、env、Nginx 或证书**。安装失败/健康失败则按第 12 章判断恢复方案；不要连续重试造成迁移状态混乱。

### 11.3 仅修改服务器配置

- 环境变量变化：先受限备份 `account-book.env`，在服务器编辑器内改值，检查权限为 root:root 600，再 `systemctl restart account-book.service`，执行健康等待与业务验证。普通 env 值变化无需 daemon-reload；配置由重启后的进程读取。
- unit / drop-in 变化：先备份；`systemd-analyze verify /etc/systemd/system/account-book.service` 成功后 `systemctl daemon-reload`，再重启与验收。
- Nginx 变化：备份对应站点与片段，`nginx -t` 成功后 `systemctl reload nginx`，再做公网验证。不能把检查失败后的 reload 当成“尝试修复”。
- 微信 AppSecret 或 Pepper 变化：属于专门的密钥轮换，需明确影响范围与恢复安排，不能在普通功能发布中顺便更换。

### 11.4 小程序更新

1. 修改页面、逻辑及必要的接口调用，同步相关测试。
2. 更新 `app-info.ts` 展示版本；若调整 `package.json` 项目版本，同步其 lockfile 元数据。后台上传版本与展示版本对应。
3. 运行第 9.2 节验证，开发者工具重新编译上传。
4. 按第 9 章体验 → 审核 → 发布。只修改前端时无须为了“上线”重启服务器。
5. 发布后检查实际正式版本，保留旧后端接口直到确认可以下线。

## 12. 发布失败、回滚与数据库恢复

### 12.1 先判断失败阶段

| 失败阶段 | 处理 |
|---|---|
| 本地测试/构建/上传失败 | 不切换线上；修复后生成新包 |
| 服务器摘要或安装前检查失败 | 不执行后续安装；旧服务已停且尚无改动时可恢复旧服务 |
| 新 JAR 健康失败，数据库仍兼容旧版 | 停止新服务，恢复旧 JAR，等待健康并验证业务 |
| 新 JAR 已改变数据库，旧版不兼容 | 不直接运行旧 JAR；优先修复兼容问题或按经过演练的数据恢复方案处理 |
| 小程序审核未通过 | 已发布旧版本保持可用；修复材料/代码重新提审，不随意回退正常后端 |
| 新小程序正式发布后出现问题 | 看后台是否提供适用回退能力；有则按其规则操作，否则上传修复版提审；后端同时保证新旧版本兼容 |

### 12.2 仅回滚 JAR

前提：旧 JAR 仍存在、摘要匹配，且与当前数据库和仍在使用的小程序版本兼容。以下不会回滚数据库或配置。

服务器 Bash，从发布前记录复制真实旧路径：

```bash
(
set -euo pipefail
OLD_JAR='/opt/account-book/releases/替换为发布前记录的旧版本.jar'
case "$OLD_JAR" in
  /opt/account-book/releases/*.jar) ;;
  *) exit 1 ;;
esac
test -f "$OLD_JAR"
runuser -u accountbook -- test -r "$OLD_JAR"
ROLLBACK_LINK="/opt/account-book/.current.jar.rollback.$$"
test ! -e "$ROLLBACK_LINK"
test ! -L "$ROLLBACK_LINK"
systemctl stop account-book.service
ln -s -- "$OLD_JAR" "$ROLLBACK_LINK"
mv -Tf -- "$ROLLBACK_LINK" /opt/account-book/current.jar
readlink -f /opt/account-book/current.jar
)
```

先按记录核对旧 JAR 摘要，再运行第 7.5 节启动、等待和第 8 章检查。若此次改过 env/unit/Nginx，应分别判断是否恢复其受限备份，不能只换 JAR 后声称完整回滚。

`install-release.sh` 默认最多保留 3 个包，且 `--no-restart` 也会清理；第 11 章特意增大 keep 避免升级时删掉回滚目标。验收后再人工制定保留策略；发布目录不是长期档案。

### 12.3 恢复演练

先在**隔离环境的新库**验证备份，不直接把历史备份覆盖正式库：

1. 核对 SHA-256 与 `gzip -t`；另存异地受保护副本。
2. 使用有恢复权限的账号，在独立 MySQL 实例或经确认无用途的新库建立演练目标，例如 `account_book_restore_drill_日期`。
3. 检查 SQL 中的固定库名、DEFINER、例程/事件和跨库引用，防止恢复后访问正式库；同机恢复尤其要检查事件调度影响。不能仅改 mysql 命令的目标库就假定完全隔离。
4. 导入备份；核对表结构、Flyway 历史、关键表行数、金额及成员权限数据。
5. 需要启动验证时使用隔离配置和端口；Flyway 启动可能改表，不能称为“只读启动”。用对应版本 JAR 或演练待发布迁移。
6. 记录备份时间、恢复耗时、核对结果及执行人。演练库清理另核对目标，避免把删除命令用于正式库。

参考仓库 `deploy/scripts/restore-mysql.md` 的流程，但其中 `account_book`、默认 mysql 命令及“数据库仅回环监听”的旧示例不符合本机基线，应使用本手册的真实库名、`/opt/mysql8/bin/mysql` 和实际网络状态。备份账号未必拥有创建库/恢复对象权限，执行前核实。

### 12.4 正式数据恢复

正式恢复会覆盖/改变数据，先确认恢复点及该时间之后的新账目处理方式：

1. 停止本项目后端，确认无其他写入；保留当前损坏/异常库的备份及日志。
2. 在隔离库验证拟恢复备份，明确将损失或需补录的数据范围。
3. 依据演练结果执行恢复，使用与恢复后数据库兼容的 JAR 和配置。
4. 验证健康、迁移历史、账本/成员/账目及统计，再恢复访问。
5. 记录恢复结果、恢复点之后的数据补录及事故原因。

不把生产整库导入写成可盲贴的日常回滚命令；JAR 回滚与数据恢复是不同操作。

## 13. 运维：备份、续期与巡检

### 13.1 配置定时备份（待实施）

也可沿用已验证的 socket 认证方式，但不得假定 root 无需密码。应用账号不因此改为 root。将发布包的 `backup-mysql.sh` 校验后安装为：

```bash
bash -n /root/server-upload-实际编号/backup-mysql.sh
install -o root -g root -m 0750 /root/server-upload-实际编号/backup-mysql.sh \
  /usr/local/sbin/account-book-backup-mysql
```

先手工执行一次并检查输出路径对应的压缩包与摘要：

```bash
env PATH=/opt/mysql8/bin:/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin \
  /usr/local/sbin/account-book-backup-mysql \
  --defaults-extra-file /etc/account-book/backup.cnf \
  --database account_book_dev --backup-dir /var/backups/account-book \
  --retention-days 7 --weekly-keep 4
```

脚本默认库是 `account_book`，因此每次必须传实际库名。它按时间清理旧日备份，UTC 星期日另外复制到 weekly，保留最近 4 个文件，不保证一定覆盖 4 个不同自然周。gzip 不提供加密，需配合受保护存储及异地副本。

手工备份成功后，创建以下专属 systemd 文件（如同名文件已存在，先核对并备份，不直接覆盖）。

`/etc/systemd/system/account-book-backup.service`：

```ini
[Unit]
Description=MyTallyBook database backup
After=mysql8.service

[Service]
Type=oneshot
User=root
UMask=0077
Environment=PATH=/opt/mysql8/bin:/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin
ExecStart=/usr/local/sbin/account-book-backup-mysql --defaults-extra-file /etc/account-book/backup.cnf --database account_book_dev --backup-dir /var/backups/account-book --retention-days 7 --weekly-keep 4
```

`/etc/systemd/system/account-book-backup.timer`：

```ini
[Unit]
Description=Daily MyTallyBook database backup

[Timer]
OnCalendar=*-*-* 03:15:00 Asia/Shanghai
Persistent=true
Unit=account-book-backup.service

[Install]
WantedBy=timers.target
```

文件 root:root 644。服务器验证、启用：

```bash
(
set -euo pipefail
systemd-analyze calendar '*-*-* 03:15:00 Asia/Shanghai'
systemd-analyze verify /etc/systemd/system/account-book-backup.service \
  /etc/systemd/system/account-book-backup.timer
systemctl daemon-reload
systemctl start account-book-backup.service
systemctl show account-book-backup.service -p Result -p ExecMainStatus
journalctl -u account-book-backup.service -n 30 --no-pager
systemctl enable --now account-book-backup.timer
systemctl list-timers account-book-backup.timer --all
)
```

预期 Result=success、ExecMainStatus=0，日志有新备份路径，timer 有下一次执行时间。oneshot 成功后显示 inactive 可以正常；以执行结果和实际文件为准。还需核对真实定时触发记录并验证恢复，才把本项改为“完成”。timer 不会自动通知人，另行落实失败检查或告警渠道。

### 13.2 备份与配置归档

- 发布前保留数据库备份、旧 JAR 与摘要、源码版本、受限 env/unit 备份及发布记录。
- 至少定期把备份复制到独立故障域的受保护存储，并验证可取回；同一服务器上的备份不能覆盖整机损坏风险。
- 每月安排一次恢复演练；有迁移的发布在发布前额外演练。
- `.sha256` 可能包含原绝对路径。移动文件后，应计算新位置文件的摘要与记录值比较，避免实际又校验了原位置。
- 不把数据库 dump、密钥、完整隐私日志放到普通项目仓库。备份中的个人信息按生产数据保护。

### 13.3 证书续期（当前为手工方式）

没有 DNS authentication hook 的手工证书不能自动续期，安装了 `certbot.timer` 也不代表续期已可用。后续自动化需选择 DNS 服务商支持的插件或受控 hook，配置权限受限的 DNS API 凭据，验证续期演练及成功后的 Nginx reload。当前这项尚未实现。依据：[Certbot 手工验证与续期](https://eff-certbot.readthedocs.io/en/stable/using.html#manual)。

### 13.4 日常检查与定位

服务器只读检查：

```bash
systemctl is-active mysql8.service nginx account-book.service
systemctl is-enabled mysql8.service nginx account-book.service
curl -fsS --connect-timeout 2 --max-time 5 http://127.0.0.1:7631/actuator/health
readlink -f /opt/account-book/current.jar
df -h
journalctl -u account-book.service --since '30 minutes ago' --no-pager
```

日志留在管理环境内排查，对外提供前去除个人信息和秘密。不要用 `cat account-book.env` 或打印进程环境来排错。

| 故障 | 排查顺序 |
|---|---|
| 无法解析域名 | A/AAAA/权威 DNS → 本地/公共缓存 → 正常域名请求 |
| HTTPS 超时 | DNS目标 → 云安全组443 → nginx状态/监听 → 服务器网络 |
| TLS 证书错误 | 域名、到期日、完整链、实际对外证书、Nginx是否reload |
| 502 | account-book服务 → 回环健康 → Java日志/数据库/迁移 |
| 登录失败 | AppID一致性、后端AppSecret配置、服务器出站微信443、脱敏错误日志 |
| 旧邀请/会话突然失效 | 是否轮换Pepper、凭据过期/撤销、是否连接了另一环境 |
| 启动频繁失败被限流 | 先修配置/迁移问题；确认unit已加载后reset-failed，再有界启动验收 |
| 本地启动找不到或锁住JAR | 是否在主目录、是否有本项目进程占用、构建产物是否完整；不终止其他Java |

## 14. 每次发布记录模板

将模板复制为当次记录填写，可以追加到本手册或单独保存至 docs。敏感信息只记录保存位置，不记录值。

| 字段 | 填写内容 |
|---|---|
| 业务版本 / 发布编号 | 例如 1.0.1 / 实际时间戳 |
| 需求与改动范围 | 前端 / 后端 / 数据库 / 配置 |
| 源码状态 | 分支、提交号或未提交改动说明；不将“有提交号”等同于包含全部工作区改动 |
| 测试结果 | 命令、执行时间、通过/失败/跳过、真实库测试是否完成 |
| 数据库 | account_book_dev；升级前/后 Flyway 版本；迁移演练结果 |
| 数据备份 | 实际路径、SHA-256、可恢复性证据 |
| 上一版本 | JAR路径、摘要、配置备份位置 |
| 新版本 | JAR路径、摘要、安装时间 |
| 后端验收 | systemd、回环UP、公网健康、匿名401、旧客户端验证 |
| 小程序上传 | 上传版本、工具版本、基础库、上传结果 |
| 体验验收 | 测试人、设备/网络、用例与结果、测试数据清理 |
| 审核 | 提交时间、材料/体验路径、结果或驳回原因 |
| 正式发布 | 发布时间、发布方式、正式版验证 |
| 回滚条件 | 数据库兼容性、旧客户端兼容性、可用恢复点 |
| 运维 | 证书实际到期日、备份状态、负责人 |
| 问题与遗留项 | 原因、修复、仍待处理的事项 |

**一次发布的完成标准：** 本次需要更新的组件已部署/发布，实际正式入口验证通过，数据与权限符合预期，回滚材料可用，发布记录完整。对首次上线，体验版正常运行不能代替代码审核和正式发布；对后续迭代，文档修改不能代替开发隔离、脚本修复或运维任务的实际执行。
