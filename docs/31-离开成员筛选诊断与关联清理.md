# 离开成员筛选诊断与关联清理

范围按用户确认：只清理已离开成员的账本关联，保留历史账单和用户账号。本次仅修改主工作区、准备脚本和本地验证，没有连接生产数据库或执行清理。

## 当前逻辑与截图原因

- 主动退出：`MemberService.remove` 将 `ledger_member.status` 改为 `LEFT`；被踢出：改为 `REMOVED`。同时写入 `removed_at`、撤销该用户会话及其有效邀请、记录审计。成员关联行会保留，不物理删除账号或账单。
- 重新加入仍需要有效邀请。有旧关联时按同一用户重新启用为普通成员；清理后重新加入会建立新成员关联，但仍使用原账号。其历史账单也仍归原 `created_by`。
- 当前 `/api/v1/entries/creators` 只查询账本 1 中成员状态和账号状态均为 `ACTIVE` 的人员。所有者可选本人、其他有效成员、全部成员；普通成员及管理员仅能查询本人。
- 老版本曾把 `book_entry.created_by` 与成员查询合并，所以离开的人只要有历史账单，仍可能出现在创建人选项中。清理成员关联不会修复这条旧查询，也不应为此删除历史账单。
- 当前前端还存在一个已复现的缓存缺口：另一手机退出后，所有者打开成员页已看到最新两人，15 秒内返回首页或统计时可能沿用旧三人的筛选选项。已修改 `MemberFlow.list`，成功读取成员列表后使 tab 缓存失效；返回首页、明细、统计会重新查询创建人，离开人员的旧选择会回落到本人。普通 tab 切换继续使用原有缓存。

本次前端修改需要上传、发布小程序才会影响手机正式版。当前无法仅凭启动日志确认服务器运行的是哪一版后端。

## 上传与运行清理脚本

上传本机打包目录 `target/member-cleanup-20261008/` 到服务器 `/root/`，保持以下结构：

```text
/root/member-cleanup-20261008/
  scripts/cleanup-departed-members.sh
  sql/cleanup-departed-members.sql
  README.md
  SHA256SUMS
```

服务器运行的正式库在现有日志中名为 `account_book_dev`。脚本默认使用该库、账本 ID 1、MySQL 客户端 `/opt/mysql8/bin/mysql` 和 socket `/opt/mysql8/run/mysql.sock`。如真实配置不同，请用 `--database`、`--mysql`、`--socket` 指定。脚本由 MySQL 客户端提示输入数据库密码，不把密码写入命令或脚本。

完整上传后校验，再预览；默认不提交任何删除：

```bash
cd /root/member-cleanup-20261008
sha256sum -c SHA256SUMS
bash /root/member-cleanup-20261008/scripts/cleanup-departed-members.sh
```

输出依次包含前置校验、当前有效创建人、准备清理的 `departed_member_id/user_id/status`、保留账单数量及最终结果。预览结果是 `PREVIEW_ROLLED_BACK`，`deleted_members` 为 0；若报错，不继续执行清理。

确认候选人员后，清理全部已退出、被踢出的非所有者关联：

```bash
bash /root/member-cleanup-20261008/scripts/cleanup-departed-members.sh --mode apply
```

也可以只清理预览中指定的 `user_id`。例如用户 ID 为 3：

```bash
bash /root/member-cleanup-20261008/scripts/cleanup-departed-members.sh --user-id 3
bash /root/member-cleanup-20261008/scripts/cleanup-departed-members.sh --mode apply --user-id 3
```

正式执行结果是 `APPLIED`，`deleted_members` 为实际删除关联数。再次执行不会重复删除，通常为 0。可以重新运行预览核对剩余关联。全过程不停止应用服务；事务会短暂占用成员写锁，锁等待超过 10 秒会报错退出。

## 清理边界

唯一持久删除语句只操作 `ledger_member`，条件为账本 1、`LEFT/REMOVED`、非 `OWNER`，且不是 `ledger.owner_user_id`。有效成员不删除，账号被禁用也不等于已退出。

脚本保留全部 `app_user`、`book_entry`（含软删除流水）、邀请、会话、审计、分类、资金账户。使用实际数据库和账本状态校验，要求已完成 V2 结构调整、核心表使用 InnoDB、没有指向成员表的外键或成员表触发器、所有者一致且有效。保持外键检查启用，不使用 `--force`。事务加锁顺序与应用一致，并在提交前检查账号数、账单数和有效成员数未改变。任一前置校验失败会中止；未提交的事务在连接关闭时回滚。

成员关联中如果有不同于账号昵称的 `display_name`，物理清理后历史账单创建人显示会回退为 `app_user.nickname`。账单内容和归属不会改变。所有者选择“全部成员”仍可查看保留的离开成员历史账单；创建人下拉框仅显示当前有效成员。

SQL 使用事务和会话临时表。临时表创建不会隐式提交持久事务；提交与回滚规则参考 [MySQL 8.0 事务文档](https://dev.mysql.com/doc/refman/8.0/en/commit.html) 和 [临时表的隐式提交说明](https://docs.oracle.com/cd/E17952_01/mysql-8.0-en/implicit-commit.html)。

## 仅清理陈泓宇（单文件）

按用户后续指定，另提供 `deploy/scripts/cleanup-chen-hongyu-member.sh`。它内嵌 SQL，不依赖前面的打包目录；通过 SFTP 把这一份文件上传为 `/root/cleanup-chen-hongyu-member.sh`。

```bash
# 可选：先预览，不删除
bash /root/cleanup-chen-hongyu-member.sh

# 执行指定人员关联清理
bash /root/cleanup-chen-hongyu-member.sh --apply
```

只在账本 1 中对昵称或成员显示名精确匹配“陈泓宇”，匹配检查包含有效成员和所有者。锁定成员、账号之后确定唯一用户 ID，不猜人员 ID。同名超过一人、仍为有效成员、角色为所有者或属于当前所有者时，拒绝清理；找不到关联或已清理时删除 0 行。即使未匹配，候选和 DELETE 也必须满足 `matched_members = 1` 与精确用户 ID，不会扩大为全部人员。

沿用已确认的范围：仅删除其 `LEFT/REMOVED` 成员关联，保留账号、历史账单和其他数据。SQL 失败时不提交。数据库仍默认为现有正式服务所用的 `account_book_dev`，MySQL root 密码由客户端提示输入。本轮只是提供脚本，未在服务器执行。
