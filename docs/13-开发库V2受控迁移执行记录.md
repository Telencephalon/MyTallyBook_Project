来源：用户在 DBeaver 执行只读 SQL 后复制的完整结果，不是代理重新连接 JDBC 获取的结果。逐约束按序拼接后解码如下：

| 约束 | 分块 / 字节 | 解码与批准规则的对应关系 |
|---|---|---|
| ck_ledger_singleton | 1 / 21 | singleton_key = 1 |
| ck_invite_status | 3 / 91 | 状态仅为 ACTIVE、USED、REVOKED、EXPIRED |
| ck_invite_use_state | 5 / 173 | USED 时 used_by、used_at 都非空；其他状态时两者都为空 |

两条邀请约束分别含 8 个、4 个 `5C27` 字节对，即真实的反斜杠加单引号。旧规范化方法只处理紧邻普通单引号的字符集前缀，未处理这种元数据表示，因此这些原始值无法匹配批准表达式。它们表达的业务规则没有因此变成错误规则；无需修改数据库 CHECK。

修复范围限定为本地 `DevV2Migration.java` 的元数据规范化及其回归测试。以原始 HEX 解码值作为测试输入，只兼容实际出现的转义文字表示，仍严格比较运算符、状态集合、NULL 条件和逻辑分组。不得整体删除反斜杠、只匹配约束名或关键词、修改 V1/V2，也不增加重跑迁移行为。

这能确认一个可复现的后置校验缺陷；13:32 日志仅保存异常类型，不能因此宣称其他后验项目已全部通过。保留原异常事件、V1 备份和历史记录，不补写或伪造 `migration_complete` / `migration-manifest.json`。
