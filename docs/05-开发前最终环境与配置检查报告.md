## 3. 开发前必须处理的 3 项门禁

### 3.1 门禁一：确认生产数据库与 Flyway V1 状态

仓库中存在 `V1__init_schema.sql`，但本地无法确认它是否已经在京东云数据库执行。这个状态决定下一步能不能继续编辑 V1：

- 如果 `flyway_schema_history` 不存在，或者 V1 从未在任何需要保留的数据库成功执行，可以先修订 V1，再执行首次迁移。
- 如果 V1 已经成功执行，**不得修改 V1**，否则会产生 Flyway checksum 不一致；后续调整必须创建 `V2__...sql`。

在京东云 Ubuntu 上执行以下只读命令：

```bash
mysql --version

mysql -uroot -p --table -e "
SELECT VERSION() AS mysql_version,
       @@GLOBAL.character_set_server AS character_set_server,
       @@GLOBAL.collation_server AS collation_server,
       @@GLOBAL.lower_case_table_names AS lower_case_table_names,
       @@GLOBAL.max_connections AS max_connections,
       @@GLOBAL.transaction_isolation AS transaction_isolation,
       @@GLOBAL.group_concat_max_len AS group_concat_max_len,
       @@GLOBAL.log_bin_trust_function_creators AS log_bin_trust_function_creators,
       @@GLOBAL.innodb_buffer_pool_size AS innodb_buffer_pool_size;
"

mysql -uroot -p --table -e "
SELECT SCHEMA_NAME, DEFAULT_CHARACTER_SET_NAME, DEFAULT_COLLATION_NAME
FROM information_schema.SCHEMATA
WHERE SCHEMA_NAME = 'account_book';

SELECT TABLE_NAME
FROM information_schema.TABLES
WHERE TABLE_SCHEMA = 'account_book'
ORDER BY TABLE_NAME;

SELECT COUNT(*) AS flyway_history_exists
FROM information_schema.TABLES
WHERE TABLE_SCHEMA = 'account_book'
  AND TABLE_NAME = 'flyway_schema_history';
"
```

如果最后一项返回 `1`，再执行：

```bash
mysql -uroot -p --table account_book -e "
SELECT installed_rank, version, description, type, script, checksum, installed_on, success
FROM flyway_schema_history
ORDER BY installed_rank;
"
```

需要把输出保存到安全位置，但不要把数据库密码写进命令、截图或 Git。

### 3.2 门禁二：补齐后端安全配置入口并做真实数据库联调

主配置 `account-book-server/src/main/resources/application.yml` 保持本地默认值；`application-prod.yml` 已将生产后端固定为 `127.0.0.1:7631`，并默认连接同机 `127.0.0.1:3306/account_book`。密码只通过 `DB_PASSWORD` 环境变量注入。测试 profile 仍排除 DataSource、JPA 和 Flyway，因此构建成功仍不能代替真实 MySQL/Flyway 联调。

开发前需要增加“只引用环境变量、不包含秘密值”的共享配置，并在本机创建被 Git 忽略的 `application-local.yml` 或 `.env`。至少需要以下参数：

```text
DB_URL
DB_USERNAME
DB_PASSWORD
WECHAT_APP_ID
WECHAT_APP_SECRET
APP_BOOTSTRAP_KEY
APP_TOKEN_PEPPER
```

要求：

- AppSecret、数据库密码、初始化口令和 Pepper 只进入本机/服务器受限配置，不进入 Git。
- 初始化口令至少使用足够长的随机值，首次成功初始化后立即失效，并从生产环境文件删除后重启服务。
- 第一次真实联调应使用独立开发库或可丢弃测试库，不要直接拿生产数据做迁移试验。
- 增加一个会实际启动 MySQL、JPA 和 Flyway 的集成验证；现有 `application-test.yml` 只能保留为无数据库的快速上下文测试。

### 3.3 门禁三：先定稿 V1/V2，再开始持久化业务代码

当前 V1 表结构覆盖了主要实体，但以下约束与已经确认的需求仍不完全一致：

| 已确认需求 | 当前 V1 | 开发前处理建议 |
|---|---|---|
| 只维护一个固定共享账本 | `ledger` 可创建多行 | 加单账本约束，或固定使用唯一 ID 并在服务层和迁移中保证 |
| 第一个输入正确初始化口令的用户成为唯一所有者 | `app_config` 只有 `initialized` | 设计初始化口令校验/失效字段或明确只在环境变量中校验，并用一个事务锁定初始化行、创建用户/账本/OWNER 成员 |
| 邀请限时且单次使用 | `max_uses` 允许 1 到 9 | 第一版固定为 1；接受邀请时锁行并原子更新使用状态 |
| 最多 10 名活跃成员 | 字段有上限但没有并发计数保护 | 接受邀请事务中锁定账本并重新统计活跃成员 |
| 按账单创建人统计 | 有 `created_by`，但缺少对应统计索引 | 增加 `(ledger_id, created_by, entry_date)` 索引，并统一统计口径为 `created_by` |
| 普通成员只能改删自己的账单 | 数据库无法单独表达完整权限 | 服务层按当前用户和角色授权；OWNER/ADMIN 可处理所有账单 |
| 分类、账户、成员必须属于同一账本 | 外键只验证记录存在 | 服务层写入前验证相同 `ledger_id`，关键操作放在同一事务 |

这些问题不要求把所有规则都强塞进数据库，但必须在迁移、事务和服务授权之间明确责任，避免实现后再改数据模型。
